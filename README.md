# Матчинг товарных карточек — GBM-пайплайн

Решение задачи классификации пар товаров-кандидатов (ecup26-matching). Пары
собраны заранее, retrieval-часть решать не нужно — требуется для каждой пары
$(i, j)$ выдать $\hat{p}_{ij} \in [0, 1]$, вероятность того, что это одна и та
же товарная позиция.

Ключевое ограничение задачи — **скорость инференса**. Это определило выбор
архитектуры: вместо cross-encoder'а (как в baseline) используются дешёвые
строковые признаки поверх градиентного бустинга. Ни одной нейросети в рантайме,
ни одного обращения к GPU.

---

## 1. Постановка

Пусть $x_i = (\text{name}_i, \text{attributes}_i, \text{category}_i)$ — карточка
товара. Требуется построить

$$f: (x_i, x_j) \mapsto \hat{p}_{ij} \in [0,1].$$

Обучающая выборка размечена из двух источников с принципиально разной природой:

| Источник | Объём | Природа $t$ | Смысл |
|---|---:|---|---|
| `matches.parquet` | 365 654 | $t \in \{0, 1\}$ | ручная разметка, ground truth |
| `matches_llm.parquet` | 11 187 780 | $t \in [0, 1]$ | вероятностная разметка LLM |

Каталог: `items.parquet` — 13 397 761 товар, 20 категорий;
`items_human.parquet` — 711 304 товара (подмножество, покрывающее ручные пары).

Асимметрия $\approx 30{:}1$ в пользу LLM-разметки — центральный факт, вокруг
которого построена вся методология валидации ниже (§5).

---

## 2. Признаки

13 признаков на пару, все — из стандартной библиотеки Python, без внешних
зависимостей в рантайме. Обозначения: $s_1, s_2$ — строки названий,
$T_1, T_2$ — множества токенов названий, $A_1, A_2$ — словари атрибутов,
$K_1 = \operatorname{dom} A_1$, $K_2 = \operatorname{dom} A_2$ — множества
ключей атрибутов, $V_1, V_2$ — множества токенов значений атрибутов.

Токенизация: `[a-zA-Zа-яА-ЯёЁ0-9]+` после приведения к нижнему регистру.

### 2.1 Признаки по названию

**`name_seq_ratio`** — коэффициент Рэтклиффа—Обершелпа:

$$\text{ratio}(s_1, s_2) = \frac{2M}{|s_1| + |s_2|},$$

где $M$ — суммарная длина всех совпадающих блоков, найденных рекурсивным
алгоритмом наибольшей общей подстроки (`difflib.SequenceMatcher`). В отличие от
расстояния Левенштейна, учитывает порядок символов и устойчив к перестановке
крупных блоков — что важно для товарных названий вида
`«бренд артикул тип»` vs `«тип бренд артикул»`.

Сложность — $O(n^2)$ в худшем случае; это самый дорогой признак в наборе, и он
же определяет пропускную способность пайплайна (≈11 тыс. пар/с однопоточно).

**`name_token_jaccard`** — индекс Жаккара по токенам:

$$J(T_1, T_2) = \frac{|T_1 \cap T_2|}{|T_1 \cup T_2|}.$$

Дополняет предыдущий признак: инвариантен к порядку слов, но не видит опечаток
и морфологии. Пара $(\text{ratio}, J)$ разделяет два разных типа расхождений —
«те же слова в другом порядке» ($J$ высок, ratio ниже) и «похожие слова с
опечатками» (наоборот).

**`name_len_ratio`**, **`name_len_diff`**:

$$\frac{\min(|s_1|,|s_2|)}{\max(|s_1|,|s_2|,1)}, \qquad \bigl||s_1| - |s_2|\bigr|.$$

Прокси на «одна карточка — развёрнутое описание, вторая — краткое», типичный
паттерн для неполных дублей.

**`common_word_count`** — $|T_1 \cap T_2|$, ненормированный счётчик. В отличие от
$J$, сохраняет абсолютный масштаб: 8 общих слов из 10 и 2 из 2 дают разный
сигнал при одинаковом $J$ для второго случая.

### 2.2 Признаки по атрибутам

**`attr_key_jaccard`** — $J(K_1, K_2)$, насколько сопоставимы схемы атрибутов.

**`attr_common_key_count`** — $|K_1 \cap K_2|$.

**`attr_exact_match_ratio`** — доля совпадающих значений среди общих ключей:

$$\frac{\bigl|\{k \in K_1 \cap K_2 : A_1(k) = A_2(k)\}\bigr|}{|K_1 \cap K_2|}.$$

Самый прямой сигнал матча: совпадение по `артикул`, `партномер`, `oem-номер`
почти детерминированно означает дубль.

**`attr_value_jaccard`** — $J(V_1, V_2)$, устойчив к расхождению в именовании
ключей (когда один продавец пишет `бренд`, другой — `производитель`).

**`attr_count_diff`** — $\bigl||A_1| - |A_2|\bigr|$, полнота заполнения карточки.

**`category_match`** — $\mathbb{1}[c_1 = c_2]$.

### 2.3 Семантика пропусков

Отдельный содержательный вопрос — что возвращать, когда признак **не определён**.
Наивная реализация возвращала $J(\varnothing, \varnothing) = 1$ («два пустых
множества идеально совпадают»), при этом `attr_exact_match_ratio` в аналогичной
ситуации возвращал $0$. То есть отсутствие информации кодировалось то как
максимум, то как минимум шкалы — и в первом случае модель получала
«идеальное совпадение» там, где сравнивать было нечего. Для карточек с пустыми
атрибутами это прямой генератор ложных срабатываний.

Текущая конвенция:

$$J(A, B) = \begin{cases}
\text{NaN}, & A = B = \varnothing \quad \text{(нет информации)} \\
0, & A = \varnothing \veebar B = \varnothing \quad \text{(реальное различие)} \\
\dfrac{|A \cap B|}{|A \cup B|}, & \text{иначе}
\end{cases}$$

`HistGradientBoostingClassifier` обрабатывает NaN нативно: на каждом сплите
пропуски отправляются в ту ветвь, которая даёт больший прирост, то есть
оптимальное направление **выучивается из данных**, а не задаётся руками.

Дополнительно введены индикаторы `attrs1_empty`, `attrs2_empty` —
$\mathbb{1}[|A| = 0]$. Пустота карточки становится наблюдаемым признаком, а не
маскируется под значение similarity.

## 3. Работа с двумя источниками разметки

Бинарная метка: $y = \mathbb{1}[t \geq 0.5]$.

Веса объектов:

$$w_i = \begin{cases}
\lambda_H, & i \in \text{human} \\
2\,|t_i - 0.5|, & i \in \text{LLM}
\end{cases}$$

Множитель $2|t - 0.5|$ отображает $[0,1] \to [0,1]$ с минимумом в $t = 0.5$:
уверенные суждения LLM ($t \to 0$ или $t \to 1$) получают полный вес, а
неуверенные — вес, стремящийся к нулю. По сути это линейная аппроксимация
уверенности классификатора-разметчика.

Пары с $t = 0.5$ **удаляются**, а не просто получают $w = 0$: правило
$y = \mathbb{1}[t \geq 0.5]$ пометило бы их как положительные, и они остались бы
в матрице как строки с меткой, не подкреплённой никаким сигналом. Нулевой вес
исключает их из функции потерь, но не из статистик разбиения и не из
`validation_fraction` внутри самого бустинга.

$\lambda_H$ не выбирается умозрительно, а перебирается по сетке
$\{1, 3, 5, 10\}$; выбирается значение с лучшим ROC-AUC на честной
валидации (§5).

## 4. Модель

`HistGradientBoostingClassifier` — гистограммный градиентный бустинг
(реализация в духе LightGBM). Минимизируется взвешенная логистическая потеря:

$$\mathcal{L} = -\sum_i w_i \bigl[y_i \log p_i + (1 - y_i)\log(1 - p_i)\bigr],
\qquad p_i = \sigma(F(x_i)).$$

Ансамбль строится аддитивно: $F_m(x) = F_{m-1}(x) + \nu\, h_m(x)$, где $\nu$ —
learning rate, а очередное дерево $h_m$ приближает ньютоновский шаг. Для
логистической потери градиент и гессиан по объекту:

$$g_i = w_i\,(p_i - y_i), \qquad h_i = w_i\,p_i(1 - p_i).$$

Оптимальное значение в листе $L$ при L2-регуляризации $\lambda$:

$$v_L^{*} = -\frac{\sum_{i \in L} g_i}{\sum_{i \in L} h_i + \lambda},$$

а прирост от разбиения узла на $L$ и $R$:

$$\text{Gain} = \frac{1}{2}\left[
\frac{(\sum_{L} g)^2}{\sum_{L} h + \lambda} +
\frac{(\sum_{R} g)^2}{\sum_{R} h + \lambda} -
\frac{(\sum_{L \cup R} g)^2}{\sum_{L \cup R} h + \lambda}
\right].$$

Здесь и виден механизм весов: $w_i$ входит и в $g_i$, и в $h_i$, то есть
масштабирует вклад объекта в выбор разбиения, а не только в итоговую потерю.

**Почему гистограммный вариант.** Признаки предварительно квантуются в 255
бинов, после чего поиск оптимального разбиения по признаку стоит $O(\#\text{bins})$
вместо $O(n \log n)$ на сортировку. При $n \approx 1.15 \times 10^7$ это
разница между часами и минутами. Дополнительно применяется приём вычитания
гистограмм: гистограмма дочернего узла получается вычитанием гистограммы
брата из родительской, что экономит проход по данным.

Гиперпараметры: `max_iter=500`, `learning_rate=0.05`, `max_depth=8`,
`l2_regularization=1.0`, ранняя остановка с `n_iter_no_change=20`.

## 5. Методология валидации

Это самая содержательная часть решения — здесь было исправлено две ошибки,
каждая из которых давала завышенную и потому бесполезную метрику.

### 5.1 Валидация только на ручной разметке

Изначально признаки human и LLM объединялись, после чего делался случайный
`train_test_split`. При соотношении $30{:}1$ валидационная выборка оказывалась
на $\approx 97\%$ размечена LLM. Формально метрика росла, но измеряла она
**согласие с LLM-разметчиком**, а не с истиной — при том что тест размечен
людьми.

Правильный порядок: hold-out выделяется из ручной разметки **до** какого-либо
смешивания, LLM-пары попадают исключительно в train, метрика считается только
на отложенной ручной части.

### 5.2 Утечка через связные компоненты

Пары не являются независимыми наблюдениями: они связаны через общие товары.
Если $(X, A)$ попала в train, а $(X, B)$ — в validation, модель на валидации
видит карточку, которую уже изучала. В товарном матчинге это усугубляется
кластерами почти идентичных карточек, порождающими десятки почти совпадающих
векторов признаков.

Формально: рассмотрим граф $G = (V, E)$, где $V$ — товары, $E$ — размеченные
пары. Разбиение должно резать не рёбра, а **связные компоненты**:

$$V = \bigsqcup_k C_k, \qquad
\text{train} = \bigcup_{k \in S} E[C_k], \quad
\text{val} = \bigcup_{k \notin S} E[C_k].$$

Компоненты строятся системой непересекающихся множеств (union-find) с сжатием
путей и объединением по рангу — амортизированная сложность
$O(|E|\,\alpha(|V|))$, где $\alpha$ — обратная функция Аккермана
(практически константа). Разбиение выполняется `GroupShuffleSplit` с
`groups = component_id`.

На ручной разметке: **345 654 компоненты на 365 654 пары** — то есть граф
распадается на множество мелких кластеров, а не на один гигантский. Поэтому
разбиение по компонентам остаётся близким к 80/20 (получилось 292 370 / 73 284).

Дополнительно закрыта та же утечка на стыке источников: из LLM-train
исключаются все пары, задевающие товары из отложенной ручной валидации.

### 5.3 Метрики

Доля положительных в ручной разметке — $0.257$. При таком дисбалансе:

- **ROC-AUC** = $P(\hat{p}_+ > \hat{p}_-)$, инвариантна к базовой ставке;
- **PR-AUC** информативнее для несбалансированной задачи; базовый уровень
  случайного классификатора равен доле позитивов, т.е. $0.257$.

Важности признаков считаются через **permutation importance** на отложенной
ручной валидации, а не через встроенные impurity-based важности — последние
систематически завышают вклад признаков с большой мощностью множества значений.

## 6. Результаты

Group-aware валидация, только ручная разметка в hold-out.

**Обучение только на ручной разметке** (`--skip_llm`):

| $\lambda_H$ | ROC-AUC | PR-AUC |
|---|---:|---:|
| 1 | 0.7494 | 0.5275 |
| 3 | **0.7496** | 0.5273 |

**Обучение на объединении human + LLM:**

| $\lambda_H$ | ROC-AUC | PR-AUC |
|---|---:|---:|
| 1 | 0.7119 | 0.4780 |
| 3 | 0.7180 | 0.4867 |

### Главное наблюдение

**Добавление 11 млн LLM-размеченных пар ухудшило качество** на честной ручной
валидации: $0.7496 \to 0.7180$ по ROC-AUC. При этом рост $\lambda_H$ метрику
улучшает — то есть чем сильнее подавлен вклад LLM-разметки, тем лучше результат.

Наиболее правдоподобное объяснение — сочетание двух эффектов:

1. **Сдвиг распределения.** LLM-пары строятся по всему каталогу
   (12.4 млн товаров), ручные — по узкому подмножеству (711 тыс.). Это разные
   популяции пар, и оптимум на одной не является оптимумом на другой.
2. **Шум разметки.** При $30{:}1$ даже умеренная доля ошибок LLM доминирует над
   чистым сигналом. Взвешивание $2|t-0.5|$ подавляет неуверенные суждения, но не
   уверенно-ошибочные — а именно они наиболее вредны.

Это не повод отбрасывать LLM-данные, но повод перестать использовать их как
равноправную добавку к train (§7).

## 7. Что дальше

**По линии LLM-разметки** (главный открытый вопрос):
- использовать LLM не как источник объектов, а как источник **претрейна**:
  обучить на LLM, затем дообучить на ручной разметке;
- отбор по согласованности: оставить только те LLM-пары, где предсказание
  модели, обученной на ручной разметке, согласуется с меткой LLM;
- калибровка $t$ по ручной разметке — оценить $P(y = 1 \mid t)$ эмпирически
  вместо предположения, что $t$ уже вероятность;
- расширить сетку $\lambda_H$ вверх ($20, 50$) — тренд указывает туда.

**По линии признаков:**
- `category_match` удалить как константу;
- явное сравнение ключевых атрибутов (`артикул`, `бренд`, `oem-номер`) —
  сейчас они растворены в агрегатах, хотя совпадение по артикулу почти
  детерминирует матч;
- TF-IDF косинус с IDF-весами по каталогу: редкие токены (артикулы, модели)
  должны весить больше частотных (`для`, `шт`, `комплект`);
- числовые признаки из названий (объём, вес, размер) с допуском на единицы
  измерения.

**По линии производительности** — обязательный шаг перед сабмитом: замер
времени инференса на объёме, сопоставимом с тестовым
(`matches.parquet` + `items_human.parquet`), с проверкой укладывания в лимит.

## 8. Структура и запуск

```
matching_gbm/
├── run.py                 # инференс, CLI-контракт соревнования
├── metadata.json          # docker image + entry point
├── requirements.txt
└── src/
    ├── features.py        # признаки на пару (§2)
    ├── pipeline.py        # загрузка каталога, чанкинг, union-find (§5.2)
    └── train.py           # разбиение, перебор λ_H, обучение (§3–5)
```

Обучение:

```bash
python3 -m src.train \
  --items_human_path items_human.parquet \
  --items_full_path items.parquet \
  --matches_path matches.parquet \
  --matches_llm_path matches_llm.parquet \
  --output_model_path gbm_model.joblib
```

Инференс:

```bash
python3 run.py \
  --items_path <test_items.parquet> \
  --matches_path <test_matches.parquet> \
  --output_path submission.csv
```

### Инженерные замечания

**Выравнивание выхода.** `build_feature_matrix` возвращает ровно
`len(match_df)` строк в исходном порядке. Пары, где товар отсутствует в
каталоге, получают строку из NaN, но **не удаляются** — иначе предсказания
съезжают относительно `id1`/`id2`, и в сабмит попадает меньше строк, чем во
входном файле.

**Память.** Каталог хранится как словарь `id → (name, attributes, category)`
с сырыми строками; разбор JSON и токенизация выполняются лениво, на уровне
чанка в 200 тыс. пар, с кэшем, живущим только в пределах чанка. Ранняя версия
подготавливала все 12.4 млн товаров заранее и упиралась в лимит контейнера
(85 ГБ) — при 13 млн товаров тяжёлые Python-объекты (`frozenset`, `dict`)
дают многократный оверхед поверх исходных данных.

**Почему однопоточно.** Попытка распараллелить через `multiprocessing.Pool` с
`fork` выглядела бесплатной (copy-on-write должен был разделить каталог между
процессами), но в CPython любое обращение к объекту инкрементирует счётчик
ссылок — то есть является **записью**. Страницы «разделяемого» словаря
копируются при чтении, воспроизводя ровно ту утечку памяти, которой fork должен
был избежать; при большом RSS родителя сам `fork` дополнительно деградирует на
копировании таблиц страниц. Реальное распараллеливание этого шага требует
данных в настоящей разделяемой памяти (Arrow IPC / `shared_memory`), а не
обычных объектов Python.
